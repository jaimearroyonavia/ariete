- (decision) Paradigm: event-driven monolith + async workers. Monitoring loop pushes incidents to job queue; agent (Sidekiq worker) diagnoses async; approval signals trigger execution. Prevents: tight coupling between monitoring and remediation.
- (decision) Primary datastore: PostgreSQL (accounts, domains, infrastructure config, incidents, RAG documents). Redis: job queue (Sidekiq), session/cache only. Prevents: split-brain state; RAG embeddings and incidents in same transactional store.
- (decision) Agent execution: Sidekiq worker executes SSH/exec to remote infrastructure. [ASSUMPTION] SSH key stored encrypted in secrets backend (Rails credentials or Vault). All commands logged with timestamp, user approval, output. Prevents: unauthorized execution, audit gaps.
- (decision) State machine for incidents: Detected -> Diagnosing -> ProposedFix -> AwaitingApproval -> Executing -> Resolved/Failed. Incident record immutable; audit trail in separate table. Prevents: race conditions on approval, lost history.
- (decision) RAG with pgvector: store document chunks + embeddings in PostgreSQL. [ASSUMPTION] Use Ruby gem 'ruby-openai' for embedding calls [ASSUMPTION] offline embedding model deferred. On new incident, retrieve top-5 similar past resolutions, include in agent diagnostic context.
- (decision) API boundary: admin/web UI calls public Rails API (JSON). Agent worker calls secure internal Ruby methods directly (same process). Monitoring loop is internal HTTP client polling own endpoints or cron job. Prevents: agent over-exposed, monitoring replay loops.
- (constraint) Security boundary: remote infrastructure credentials never leave encrypted storage until agent execution; agent runs in isolated worker context with rate limits and audit log.
